# RAG Showdown

Three ways to build RAG over the same PDF, scored head-to-head on the same 10 questions. Built to teach — not to ship.

| # | System | How retrieval works |
|---|--------|---------------------|
| 1 | **Classic Vector RAG** | Docling → paragraph chunks → `sentence-transformers/all-MiniLM-L6-v2` embeddings → ChromaDB → top-k by cosine similarity |
| 2 | **Vectorless RAG (PageIndex)** | VectifyAI's hosted [PageIndex](https://github.com/VectifyAI/PageIndex) builds a hierarchical Table-of-Contents tree on their server; Claude Haiku reasons over the tree to pick relevant nodes |
| 3 | **Self-Writing Wiki** (Karpathy pattern) | One Sonnet call ingests the PDF into an interlinked markdown wiki via the rulebook in `Knowledge-Base/CLAUDE.md`. Queries read the wiki, never the raw source. |

A fourth section (`§4`) pits all three against the same 10 questions, scores them with **Claude Opus** as judge, and renders a scorecard + chart.

## The source document

`article.pdf` — Rahul Pandey's *"What does it take to be a data-driven organization?"* (DSciEr / Medium, 2023). A 12-minute strategy overview covering:

- Data-first culture
- Lakehouse architecture
- Data + AI governance frameworks
- Data-as-a-product
- Data Mesh principles
- AI Center of Excellence (CoE)
- Sustainable AI development

Lots of named lists, cross-references between body text and the References section, and quantitative claims spread across sections. Exactly the kind of structured prose where the differences between vector RAG, PageIndex, and a wiki become visible.

## Setup

### 1. Install dependencies

This is a `uv` project. From the repo root:

```bash
uv sync                                                          # installs everything in pyproject.toml
uv run python -m ipykernel install --user --name rag2-0 \
    --display-name "rag2-0 (uv)"                                 # registers the kernel
```

First run downloads ~300 MB Docling structural model and ~90 MB sentence-transformers model. Subsequent runs are cached.

### 2. Add API keys

Copy `.env.example` to `.env` and fill in two keys:

```bash
ANTHROPIC_API_KEY=sk-ant-...               # https://console.anthropic.com
PAGEINDEX_API_KEY=...                      # https://dash.pageindex.ai/api-keys (free tier)
```

Anthropic powers every per-query LLM call. PageIndex builds the §2 tree once per document on their server.

### 3. Open the notebook

```bash
uv run jupyter lab walkthrough.ipynb
```

Pick the **`rag2-0 (uv)`** kernel and run cells top to bottom.

## Notebook structure

| Section | What it does | Time |
|---|---|---|
| §0 Setup | Load `.env`, pin model IDs, define the 10 questions, set up `ask_claude()` | seconds |
| §1 Classic Vector RAG | Docling parse → chunk → embed → ChromaDB → query function | ~2 min first run, instant after |
| §2 Vectorless RAG (PageIndex) | Submit PDF → poll → fetch tree → tree-search with Claude → answer | ~1–2 min for the tree build, ~5 s per query |
| §3 Self-Writing Wiki | Seed System dashboards → 9-step Ingest workflow as one Sonnet call → wiki query function | ~3–5 min ingest, ~5 s per query |
| §4 Showdown | Run all 3 systems × 10 questions → Opus judges each answer → pandas scorecard → matplotlib chart → "Read the failures" | ~5–8 min |

Total end-to-end on a warm machine: **~15 min, well under $1**.

## What to watch for in §4

The 10 questions in §0.3 are designed to expose architectural differences, not to pick a universal winner. Each carries a `stresses` field that predicts which system should win or lose. The §4.5 "Read the failures" cell is where the comparison gets interesting — see whether the predictions hold:

- **Factual lookups** (Q1) — all three should nail it
- **Cross-references** (Q4 — paper authors in References) — vector RAG often misses; PageIndex's tree navigation should ace it
- **Multi-section synthesis** (Q6 — lakehouse ↔ data mesh) — wiki should win because it pre-synthesized at ingest
- **Quantitative facts in different sections** (Q7 — PwC + Gartner numbers) — vector RAG often surfaces only one
- **Out-of-scope** (Q9 — quantum computing) — vector RAG often hallucinates; the wiki usually declines cleanly

Numbers vary run-to-run because LLMs are non-deterministic. That's the point — you're watching architectures, not leaderboards.

## How the wiki works (§3 in plain terms)

The wiki vault under `Knowledge-Base/` is a working reproduction of the [Karpathy LLM Wiki pattern](https://github.com/VectifyAI/PageIndex). Five folders do the work:

- **`Raw/`** — sources land here (Docling drops `article.md` after §1.1). Read-only for the LLM.
- **`Sources/`** — one Source Summary per Raw item, written by the LLM at ingest.
- **`Wiki/`** — Concept, Product, Persona, and Analysis pages, all interlinked with `[[wikilinks]]`.
- **`System/`** — four dashboards the LLM maintains: `Index.md`, `Glossary.md`, `Overview.md`, `Log.md`.
- **`Archive/`** — soft-deleted pages (the rulebook supports a Prune operation, not run in this notebook).

§3.2 fires a single Sonnet call that reads `Knowledge-Base/CLAUDE.md` (the schema), parses the source, and emits the entire vault state as a JSON object keyed by file path. The notebook writes those files into `Knowledge-Base/`. After ingest, query-time reads are fast: pick relevant wiki pages from `Index.md`, read them in full, answer with `[[Page Name]]` citations.

## Cost notes

Every per-query call uses Claude (Haiku for routing, Sonnet for answers, Opus only as the §4 judge). With prompt caching enabled on the §3 system prompt, a full top-to-bottom run is well under a dollar on the reference PDF.

PageIndex hosts the §2 tree-build on their free tier — one-time per document, runs in 30–90 s server-side.
